# 子项目 A —— HD 渲染核心(探路 spike)设计文档

- 日期:2026-08-10
- 状态:已批准,待实现计划
- 所属大工程:SDLPal 真·高清重制引擎(个人自用)
- 前置说明:本文档只涉及引擎架构与构建/放大管线,面向使用者本人拥有的正版游戏数据,仅供个人使用;不涉及、也不分发任何软星(SoftStar)版权美术资源。

---

## 1. 背景与动机

SDLPal 的整条画面管线本质上是一块 **320×200、8-bit 调色板(palettized)** 的软件缓冲:

- `video.c:251` 创建 `gpScreen = SDL_CreateRGBSurface(SDL_SWSURFACE, 320, 200, 8, ...)`。
- 所有精灵为 RLE 调色板格式,统一经由 `PAL_RLEBlitToSurfaceWithShadow`(以及其 color-shift / mono-color / shadow 变体)绘制到这块 8-bit 缓冲。
- 之后转换成 32-bit `gpScreenReal`,上传到 `SDL_PIXELFORMAT_ARGB8888` 纹理,再放大/过着色器到窗口。

"真·高清重制"要显示 AI 超分出来的**大尺寸真彩图**,无法塞进 RLE 调色板格式;要原生显示,就必须把这个 8-bit/320×200 的渲染核心换成"真彩色 + 高分辨率"。同时,仙剑大量使用调色板操作实现视觉特效(淡入淡出、中毒绿、黑夜、法术闪白),这些在真彩色资源上会失效,需要逐一以色彩变换重建。

子项目 A 是整个大工程的**地基与最高风险点**,目标是在投入 AI 资源管线之前,先用一个探路 spike 证明架构可行。

## 2. 目标与非目标

### 2.1 目标
1. 建立"**双平面**"渲染核心:原版 8-bit 逻辑不动,新增 N× 真彩缓冲。
2. 跑通**绘制时资源身份识别**(内容哈希),使日后高清资源可按指纹替换。
3. 证明**调色板特效可在真彩色下重建**——以淡入淡出为试金石。
4. 交付一个可玩 build:整个游戏透过高清管线渲染(暂用实时算法放大占位),开关可回退经典路径且零回归。

### 2.2 非目标(明确推迟)
- AI 超分与高清资源的存储/加载(→ 子项目 B/C)。
- 角色 color-shift / mono-color 闪白等其余特效(→ 子项目 C)。
- 高清字体 / UI(→ 子项目 D);spike 阶段 UI/文字仍走 8-bit 底层放大。
- 战斗专属性能优化、宽屏、更高帧率。

## 3. 核心架构:双平面渲染器

### 3.1 平面定义
- **权威平面(不动):** 现有 8-bit `gpScreen` + 全部游戏绘制逻辑,继续决定"画了什么、画在哪"。我们只**观察**,不重写逻辑。
- **高清平面(新增):** 一块 N× 真彩缓冲(初始 4× = 1280×800),类型待定(SDL streaming texture / 离屏 RGBA surface)。

### 3.2 合成公式(关键设计)
```
高清平面 = 放大(8-bit 权威平面)  ← 底层,保证画面永远完整
         + 已识别精灵的高清版按缩放坐标叠加  ← 上层,可增量覆盖
         + 特效色彩变换(spike 只做淡入淡出)
```
底层兜底意味着:**即使高清资源只覆盖一部分,也绝不会有画面缺失**,支持增量上高清。非精灵绘制(直接填色/矩形/调色板刷屏)天然由放大底层覆盖。

### 3.3 绘制拦截层
在唯一咽喉——`PAL_RLEBlitToSurfaceWithShadow` 及其变体——插入一层薄拦截:
- 正常执行原 8-bit 绘制(权威平面照旧)。
- 额外记录一条 **draw command**:`{ hash(资源指纹), destX, destY, effectFlags, paletteRef }`。
- 每帧结束时(呈现前),遍历当帧 draw command,把每个精灵的高清版重绘进高清平面。

## 4. 资源身份:内容哈希

### 4.1 指纹计算
- 精灵头格式:`[可选 4 字节 0x00000002 前缀][宽 2 字节 LE][高 2 字节 LE][RLE 数据]`。
- RLE 可遍历求得精确字节长度(游程:`T < 0x80` 复制 T 字节;`T >= 0x80` 跳过 `T-0x80` 透明像素),直到产出 `宽×高` 像素。
- 对 `[宽高头 + RLE 数据]` 的字节序列做 64-bit 哈希(如 xxHash64)得到稳定 key。

### 4.2 为什么用内容哈希(而非逐加载路径打标签)
- 覆盖所有加载路径(场景 / 战斗 / UI / RNG 动画),无需逐处埋点。
- 离线 AI 管线对同一批原始字节算同样的 key,运行时天然对得上。
- 相同精灵自动共享同一份高清图(合意)。
- 代价:每次绘制一次哈希——很便宜,且**帧内按源指针缓存**(同一帧同一指针只哈希一次)。

### 4.3 spike 阶段的占位高清源
尚未接 AI:对解码后的精灵做**实时算法放大**(先 bilinear,预留 xBRZ 接口)当作高清占位,端到端验证"识别 → 取高清 → 叠加"链路。日后 B/C 只是把占位放大替换为按 key 查表的 AI 高清图。

## 5. 调色板特效策略

游戏特效清单:全屏淡入淡出、逐精灵 color-shift、mono-color 闪白、阴影。统一建模为"合成高清平面时施加的真彩色色彩变换",与 8-bit 路径读同一份状态。

**spike 只实现淡入淡出**:以一个全局亮度乘子施加到高清平面,乘子与调色板淡变进度(`palette.c` / `PAL_FadeIn/Out` 现有状态)同步。目的是立下"特效 = 与原状态同源的像素变换"这一模式,供 C 扩展其余特效。

## 6. 配置与回退

- 新增配置项 `HDRemaster`(布尔,默认 FALSE),经 `palcfg.c` / `palcfg.h` 注册。
- 打开:走高清呈现路径;关闭:走现有经典路径。
- 渲染倍率暂硬编码 4×,留一个内部常量便于日后配置化(非本 spike 目标)。

## 7. 交付物与成功标准

1. 从开场 → 地图行走 → 打开菜单,全程透过 4× 高清管线渲染。
2. 场景切换的淡入淡出观感正确。
3. 调试叠层显示:见过的唯一精灵哈希数、帧内缓存命中率——证明身份识别稳定且可复现。
4. **`HDRemaster` 关闭时与当前 build 逐像素一致(零回归)。**

## 8. 测试策略

- **单元:**
  - 哈希稳定性:同字节 → 同 key;异字节 → 异 key。
  - RLE 长度遍历正确性:遍历产出的像素数等于 `宽×高`,与解码路径一致。
- **视觉黄金对比:**
  - `HDRemaster=0` 时与现 build 关键画面逐帧一致。
  - `HDRemaster=1` 时关键画面(开场 / 地图 / 菜单 / 淡变过程)截图供人工审。
- **仪表:** 调试叠层计数器(唯一哈希数、缓存命中率、每帧 draw command 数)。

## 9. 风险与待定

1. **性能:** 战斗多精灵时每帧 4× 重合成的开销需早测;缓解:帧内指针缓存 + 尽早在战斗场景实测(Apple Silicon 预期可行)。
2. **非精灵绘制:** 由放大底层兜底,不丢画面;需确认没有绕过 `PAL_RLEBlit*` 的精灵绘制路径。
3. **亚像素对齐:** 放大底层与高清叠加之间的坐标对齐(4× 整数缩放可规避大部分问题)。
4. **管线交互:** 与现有 GLSL 着色器路径、SDL3 纹理/呈现 API 的交互与共存方式待定。
5. **draw order:** 需保证 draw command 的叠加顺序与原 8-bit 绘制顺序一致(逐帧顺序记录即可)。

## 10. 影响的关键文件(预估)

- `video.c` —— 高清平面创建、合成、呈现路径、`HDRemaster` 分支。
- `palcommon.c` —— 绘制拦截 + 内容哈希钩子(集中在 `PAL_RLEBlitToSurfaceWithShadow`)。
- `palcfg.c` / `palcfg.h` —— 注册 `HDRemaster` 配置项。
- 新增模块(建议):`hdcore.c/.h` —— 双平面状态、draw command 缓冲、哈希、占位放大、特效变换、调试叠层。
- `palette.c` —— 暴露淡变进度供特效变换读取(只读,不改逻辑)。

## 11. 后续子项目衔接

- **C(HD 资源接入):** 用查表结果替换 §4.3 的占位放大;先背景后角色;扩展 §5 其余特效。
